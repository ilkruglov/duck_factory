# duck_factory

Плагин для Claude Code и для Codex CLI (`duck-factory`). Ниже описана версия для Claude Code; чем отличается
версия для Codex — в разделе [Codex](#codex). English: [README.md](README.md). Изменения по версиям: [CHANGELOG.ru.md](CHANGELOG.ru.md).

Три навыка, из которых складывается небольшой конвейер разработки: договориться о задаче до начала, один раз
проверить результат с глубиной под размер правки и передать работу в новую сессию. Два [хука](#хуки) берегут
план и состояние работы при сжатии контекста.

| Навык | Когда запускается | Что делает |
|---|---|---|
| `grill` | сам, перед нетривиальной задачей, с кодом или без; или по `/duck-factory:grill` | Если ты одобрил список оптом или задачу предложил агент — сначала спрашивает, что из этого делать вообще. Затем опрашивает короткими раундами через окно вопросов, рекомендуемый вариант первым, и пишет в `.tmp/plans/` план на одну страницу, если работа меняет код, иначе — короткую запись решений, шагов и критериев готовности. Большой план, меняющий код, до начала работы проверяет Codex. |
| `review` | сам, после законченной правки кода; или по `/duck-factory:review` | Измеряет правку (строки кода, файлы, места вызова, обратимость), выбирает ступень, параллельно запускает встроенный `/code-review`, Codex с заданием навыка и, начиная с обычной ступени, «адвоката дьявола» Codex (в финальном ревью — ревьюера Codex и Claude на каждую группу файлов), сверяет с планом, проверяет каждую находку и отчитывается. Ещё — финальное ревью всей работы перед PR, слиянием или выпуском; проход безопасности — после твоего «да». Только находит; правки — после твоего согласия. |
| `handoff` | только по `/duck-factory:handoff` | Пишет `.tmp/handoff/<имя>.md`, чтобы новая сессия продолжила работу: цель, ограничения, решения, что сделано и чем проверено, что запущено, следующий шаг, откат. Файл начинается с указания следующей сессии сверить его с реальностью. |

## Конвейер

1. `grill` подгружает навыки по теме, закрывает решения и пишет план с критериями приёмки: полный для кода, иначе
   короткую запись.
2. Ты одобряешь план или запись; работа идёт от теста.
3. `review` запускается один раз, перед отчётом и коммитом.
4. После твоего согласия: падающий тест и фикс на каждую подтверждённую ошибку, тесты и короткое повторное ревью
   только исправлений; упрощение — один раз, в конце, Codex и агент.
5. `handoff` — когда работа продолжается в другой сессии.

Ничто здесь не заменяет твоего одобрения: `grill` ничего не меняет до подтверждения, полный план — не согласие начать
работу, а `review` никогда не правит файлы.

## grill

Запускается перед нетривиальной задачей: новая возможность или модуль, выбор между подходами, правка в нескольких
местах, работа без кода больше чем в несколько шагов (исследование, документ, настройка), неясная цель. На
исправлении ошибки или мелкой понятной правке говорит, что задача ясна, и отходит в сторону. В любом случае в
репозитории git сначала смотрит `git status`: если принятая работа другой задачи ещё не закоммичена, спрашивает,
закоммитить ли её, чтобы обычное ревью новой задачи читало только новую правку (в режиме планирования коммит ждёт
выхода из него).

Как идёт сессия:

0. **Сначала «что», потом «как».** Если ты одобрил набор задач оптом («делай всё» о списке дел, о предложениях
   агента, о чужом плане) или задачу придумал сам агент, первый раунд спрашивает только одно: что из этого
   делать вообще, с оценкой объёма каждой задачи. Вопросы о реализации идут после того, как ты сказал делать.
   О задачах, которые ты сам назвал в запросе, этот вопрос не задаётся.
1. **Навыки по теме.** Если задача касается области, которую покрывает другой установленный навык (фреймворк,
   тип системы, правила проекта), он подгружается первым: от него зависит, какие вопросы стоит задавать.
2. **Сначала факты.** Всё, что можно посмотреть в коде, конфигах и логах, смотрится, а не спрашивается.
   Решение, уже принятое — в решениях прошлого принятого плана или в правилах проекта, — берётся оттуда со ссылкой, а
   не спрашивается заново; если два плана расходятся, спрашивают тебя.
3. **Вопросы раундами**, через окно вопросов: не больше четырёх за раунд, самые важные первыми, по два–четыре
   варианта, рекомендуемый первым. В каждом вопросе есть факт, от которого зависит выбор. Со второго раунда
   последний вопрос позволяет остановиться: «хватит, остальное — по твоим рекомендациям».
4. **Подтверждение**: принятые решения и то, что взято по умолчанию без вопроса; для работы без кода оно показывает
   саму короткую запись, и твоё «да» начинает работу.
5. **План** в `.tmp/plans/<имя>.md`. Если работа меняет программный код — хук, сервис, скрипт в репозитории, CI,
   конфиг, промпт или файл данных, который читает код, — полный план на одну страницу:

```markdown
# Экспорт заметок

Status: active

Источник: «добавь экспорт заметок в CSV и JSON с выбором формата из командной строки»

Цель: `notes export --format csv|json` печатает все заметки в stdout.

Использованные навыки: нет

Решения:
- CSV через стандартный модуль csv, поля id,title,text — без новой зависимости.
- Пустое хранилище даёт пустой экспорт, а не ошибку — как в `list`.

Принято по умолчанию, не спрашивал:
- `--format` обязателен — очевидного выбора между двумя нет.

Не трогаем: формат хранения, команды add и list.

Критерии приёмки (каждый проверяется тестом, командой или тем, что пользователь смотрит названный результат):
- `notes export --format csv` печатает заголовок и строку на заметку — tests/test_cli.py::test_export_csv
- Неизвестный формат завершается ошибкой argparse — tests/test_cli.py::test_export_bad_format

Риски и открытые вопросы: нет
```

Для навыка, промпта, который не читает код проекта, документа, слайдов, исследования или настройки — даже с тестами
или проверками рядом — агент вместо плана пишет короткую запись, план, по которому работает сам: решения (умолчание
помечено), шаги и критерии готовности, у каждого своя проверка. Она возвращается после сжатия, как и полный план, а
итоговый отчёт идёт по её критериям.

```markdown
# Состав ревью по стенду

Status: active

Source: «давай сделаем как предлагаешь»

Решения:
- Codex всегда получает задание, одно на всю правку.
- «Адвокат дьявола» с обычной ступени; прицел пишет агент (по умолчанию).

Шаги:
1. Таблица ступеней и шаг 2 навыка ревью.
2. Оба README и журналы изменений.

Критерии готовности:
- Тесты проходят — `uvx pytest -q tests`.
- Ты принял список изменений поведения — смотришь его.
```

`Status` остаётся `active`, пока ты не принял результат (`done`) или не отменил работу (`dropped`). Эта строка
всегда пишется по-английски, на каком бы языке ни был план: её читают [хуки](#хуки). В строке источника — твои
слова, которыми поставлена задача. Критерий, о котором может судить только человек (как читается текст, удобна
ли настройка), проверяется показом тебе названного результата.

Для большой задачи, меняющей код (новый модуль, подход, который дорого откатывать, работа дольше одной сессии),
план затем проверяет Codex — по репозиторию, только на чтение. Его находки, которые являются решениями,
возвращаются к тебе вопросами. План без кода в Codex не уходит.

Работая по плану, навык не меняет решение молча, без вопроса переделывает то, что явно не делает согласованного
в плане, и заканчивает отчёт проходом по критериям приёмки.

## review

Запускается один раз после законченной правки кода. Отвечает на три вопроса: есть ли ошибка, совпадает ли
правка с планом и можно ли каждую находку доказать.

### Как выбирается ступень

Навык измеряет всё незакоммиченное (изменённые, проиндексированные и новые файлы) и печатает итог одной строкой:

`Ревью: обычная — 132 строки кода, 3 файла, 7 мест вызова, обратимо. Решило: больше 50 строк кода.`

- **Строки кода**: добавленные плюс удалённые, без тестов, документации и файлов данных и настроек. Строки, у
  которых изменился только отступ, не считаются (`git diff -w`): обёртка блока в `if` — это две строки, а не
  весь блок. Файл, вся правка которого — отступы, считается целиком: в Python и YAML сдвиг строки меняет
  поведение.
- **Данные, которые читает код, — это код**: таблица, фикстура, схема или промпт, которые загружает код, тесты
  или проверки проекта, считаются построчно. Неверное значение там ломает программу так же, как неверная строка.
- **Файлы**: изменённые файлы кода.
- **Места вызова**: места в коде (не в тестах), где используется функция, метод или класс с изменённым
  поведением или сигнатурой.
- **Необратимость**: то, что нельзя просто откатить — миграция данных, удаление данных или файлов, релиз,
  контракт внешнего API, формат файлов, уже лежащих на диске. Речь о том, что правка делает с уже существующим, а не
  о том, что новая функция позволит потом: добавить команду удаления — это обратимо.
- **Чувствительные пути**: пути под заголовком `Security paths` в `CLAUDE.md` проекта (или в `AGENTS.md`, если
  `CLAUDE.md` нет) — вход, права, деньги, ввод извне. Ступень они не меняют, а ревью предлагает для них проход
  безопасности (см. «Безопасность» ниже). Без списка их нет.
- **Критичные пути**: пути, которые ты перечислил под заголовком `Critical paths` в `CLAUDE.md` проекта (или в
  `AGENTS.md`, если `CLAUDE.md` нет), по одному пути или шаблону на строку. Правка, которая задевает такой путь, идёт
  на усиленную ступень. Без списка критичного нет.

| Ступень | Когда | Встроенное ревью | Codex | Сверка с планом |
|---|---|---|---|---|
| нет | строк кода не изменено | - | - | - |
| лёгкая | до 50 строк кода, 1 файл, до 5 мест вызова, обратимо | `low` | задание | нет |
| обычная | всё остальное | `medium`; `high` при нескольких группах | задание и «адвокат дьявола», с прицелом | да |
| усиленная | необратимое, критичный путь, больше 10 файлов, больше 20 мест вызова или ты попросил | `high` | задание и «адвокат дьявола», с прицелом | да |
| финальная | финальное ревью (ниже): ступень всего изменения, не ниже обычной | - | по группам и «адвокат дьявола» от основы | да |
| повторная | после исправлений | - | короткое задание только по исправлениям, Codex и субагент Claude на `medium` (ниже) | нет |

Необратимость перевешивает остальные признаки; `max` — только когда ты называешь его сам. Ступень берётся из
таблицы и ниоткуда больше: «это же ядро системы» её не поднимает — для этого есть список критичных путей. Если
под сомнением замер (необратимо ли это?), берётся ступень выше.

Откуда эти ступени. Из замера на трёх диффах с посеянными ошибками (9, 16 и 581 строка, по одному прогону на
ячейку):

| Проверка | 9 строк, 1 ошибка | 16 строк, 3 ошибки | 581 строка, 3 ошибки |
|---|---|---|---|
| встроенное `low` | 1/1, 10 с | 3/3, 25 с | 2/3, 28 с |
| встроенное `medium` | 1/1, 34 с | 3/3, 45 с | 3/3, 101 с |
| встроенное `high` | 1/1, 73 с | 3/3, 114 с | 3/3, 219 с |
| Codex | 1/1, 61 с | 3/3, 79 с | 3/3, 79 с |

`medium` и Codex нашли всё; `high` шёл вдвое дольше ради тех же ошибок и добавляет наблюдения, а не пропущенные
ошибки; `low` хватает на мелкую правку, а на большой он ошибку теряет. Пороги по местам вызова — осторожная
оценка, не замер.

Почему такие ревьюеры. Это второй замер, на двух настоящих правках из проектов автора (настольное приложение на
Rust, около 2 700 изменённых строк, и сервис на TypeScript, около 700 строк и 37 новых файлов), ошибки в которых
известны по поздним исправлениям; потом каждую находку проверили по коду, а настоящие ошибки разделили на важные
(падение, сломанная функция, потерянные или неверные данные, деньги, приватность) и мелкие. По одному прогону на
вариант, всего 22 важные ошибки:

| Ревьюеры | Нашли важных | Токены Claude | Токены Codex |
|---|---|---|---|
| Codex с заданием + его «адвокат дьявола» + встроенное `high` | 19 | 12,4M | 13,7M + «адвокат дьявола» |
| Codex с заданием + субагент Claude на группу (прежний состав) | 18 | 81,5M | 13,7M |
| собственное ревью Codex + встроенное `medium` (прежний состав при одной группе) | 12 | 6,4M | 8,7M |
| Codex с заданием один | 15 | - | 13,7M |
| собственное ревью Codex одно | 10 | - | 8,7M |
| «адвокат дьявола» Codex один | 8 | - | не записывается |

Токены посчитаны с чтением кеша, за обе правки вместе. Токены Codex взяты из журналов его сессий
(`total_token_usage`); без чтения кеша его задание потратило 0,58M, собственное ревью — 0,37M. «Адвоката дьявола»
плагин запускает временной сессией и расход не сохраняет. Codex тратит свою подписку, а не подписку Claude.

Субагенты Claude по группам нашли больше мелких ошибок (16 против 9 из 22), но за в шесть с половиной раз больше
токенов, поэтому они остались только в финальном ревью. «Адвокат дьявола» в одиночку слабее всех, но нашёл ошибку
порядка, которую не нашёл никто другой, — за пять минут и без токенов Claude. У одного ревьюера Claude уровни
`xhigh`, `high` и `medium` нашли одни и те же важные ошибки; `medium` потратил вдвое меньше токенов.

### Какие проверки идут

- **Встроенное ревью**: `/code-review` из Claude Code на уровне ступени. Оно же сверяет дифф с твоим
  `CLAUDE.md`.
- **Codex**: второе мнение другой модели, через плагин `codex@openai-codex`, — задача с заданием ниже на всё
  изменение. Начиная с обычной ступени рядом идёт его «адвокат дьявола» с прицелом, взятым из диффа: тихие отказы,
  порядок и конкурентность, миграция и её откат, упали бы тесты без этой правки.
- **Сверка с планом**: что план просил и чего нет, что сделано сверх плана, какие критерии приёмки ничем не
  проверяются. Берётся план, который `grill` написал в этой сессии, либо названный в файле передачи или в
  аргументе; без плана сверка пропускается, и отчёт об этом говорит.

Все они идут параллельно. Субагенты Claude запускаются без указания модели и поэтому идут на модели сессии;
отдельная модель для субагентов в настройках Claude Code её бы заменила.

### Финальное ревью и группы

Ревью отдельных шагов пропускает то, что видно только на всей работе целиком. В одной реальной сессии около
двадцати пошаговых ревью пропустили восемь ошибок, которые потом нашло одно ревью всего изменения в 35 файлах, и все
подтвердились по коду: половина из них — два пути в коде, написанные на разных шагах и не согласованные друг с
другом.

- **Финальное ревью.** Перед PR, слиянием (в том числе ветки или ворктри обратно) или выпуском, а также когда ты
  просишь проверить всю работу, изменением считается всё с коммита, с которого работа началась, закоммиченное или
  нет: основа из плана или файла передачи, иначе merge-base с веткой, в которую работа вольётся (но не с upstream
  своей ветки: после пуша это последний отправленный коммит). Это строка таблицы ступеней, не ниже обычной, и ревью
  всегда идёт по группам.
- **Группы.** На обычной и усиленной ступени каждый изменённый файл попадает в группу: код по подсистемам, тест — к
  коду, который он проверяет. Одна группа до 100 строк кода или при 1–2 файлах, две — до 500 строк, дальше по группе
  на три файла с округлением вверх, от двух до четырёх. Вне финального ревью группы задают только уровень
  встроенного ревью (`high` при нескольких группах) и пары повторного круга; Codex получает задание на всё изменение.
  В финальном ревью каждой группе — Codex (`task` с заданием ниже) и свежий субагент Claude с тем же заданием, все
  параллельно, и ещё «адвокат дьявола» Codex с `--base`, который видит только коммиты; встроенный `/code-review` тогда
  не запускается: он берёт весь незакоммиченный дифф, а не группу и не коммиты от основы (с `max` он всё же идёт, на
  всё изменение). Задания уходят в Codex файлом (`--prompt-file`), а не в командной строке, где оболочка выполнила бы
  их обратные кавычки. Задания каждого ревью лежат в своей папке, чтобы два ревью в одном рабочем дереве не затирали
  задания друг друга.
- **Задание** просит каждого ревьюера прочитать правила проекта (файлы инструкций, которые Claude Code или Codex
  загрузили бы для его файлов: `CLAUDE.md`, `AGENTS.md`, `.claude/rules/` и подобные) и сообщать о нарушении их как о
  находке; читать свои файлы целиком, а не только изменённые строки; для каждого нового типа, значения, сообщения или
  команды, пересекающих границу функции или модуля, найти код, который их принимает, часто вне изменения; сверить код
  с контрактами внешних API, системных вызовов и библиотек, на которые он опирается. Последние три привычки взяты у
  ревьюера [oh-my-pi](https://github.com/can1357/oh-my-pi).

### Проверка находок

Ревьюеры ошибаются тем же уверенным тоном, каким говорят правду. Каждая находка, заявляющая ошибку, проверяется
до отчёта: читается код в указанных строках и, где это дёшево, ошибка воспроизводится коротким скриптом в
`.tmp/`. Каждая находка получает отметку:

- **подтверждено** — с командой и её результатом или со строками, которые это доказывают;
- **не подтверждено** — с причиной; идёт в конце отчёта, чтобы ты мог не согласиться;
- **не проверено** — с причиной.

Дубли от разных ревьюеров сливаются, с указанием, кто нашёл.

### Отчёт

```text
Ревью: лёгкая — 9 строк кода, 1 файл, 1 место вызова, обратимо. Решило: до 50 строк кода, 1 файл.

Ошибки
1. Лимит файлов считает имена, за которыми не следят, поэтому слежение может отключиться без причины.
   watcher.py:474-477. Подтверждено: .tmp/repro_limit.py — до правки enabled=True, после неё
   enabled=False на тех же четырёх файлах. Нашли встроенное ревью и Codex.

Сверка с планом
Пропущена: плана в этой сессии нет.

Замечания по качеству
- Правка убирает комментарий, который объяснял, почему фильтр стоит до подсчёта.

Не подтверждено
Нет.

Не покрыто: настоящий сервер не запускался; файловые системы без учёта регистра не проверялись.

Исправить подтверждённую ошибку и упростить?
```

Находка, которая является решением, а не ошибкой, идёт к тебе отдельным вопросом, а не в список исправлений.

Ревью не меняет ничего, кроме файлов в `.tmp/`. Инструменты, которые оно запускает, всё же могут оставить файлы
(`uv run` пишет `uv.lock`), поэтому перед отчётом оно сверяет `git status` с тем, с чего начало, убирает
созданное им самим и говорит об этом.

### Безопасность

Ревьюеры выше ищут, где код делает не то, что задумано, а не как его можно заставить сделать то, чего не задумывали.
Это ищет отдельный проход безопасности, и запускается он только после твоего «да». Ревью предлагает его на финальном
ревью и когда правка задевает чувствительный путь (см. выше), даже когда в правке там нет строк кода; попросить можно
и на любом ревью — тогда он идёт без вопроса. Предлагается один раз на работу, на повторном круге — уже нет. В Claude
Code вопрос приходит сразу после запуска остальных проверок, и проход идёт вместе с ними. Без окна вопросов (запуск
без интерфейса, а в Codex всегда) он приходит в конце отчёта, отдельным номером от вопроса об исправлениях, и проход
начинается только после твоего ответа; если «да» на оба, он идёт первым.

Проход — ещё один ревьюер (задача Codex, без Codex — свежий субагент Claude) со своим заданием. Он читает правила
проекта и его файлы `SECURITY.md`, если они есть (ближайший к изменённому файлу главнее), и следует им там, где они
описывают модель угроз или что считать находкой. Говорит, кто дотягивается
до изменённого кода и какой ввод пересекает границу доверия; затем проверяет инъекции, обход входа и прав, данные
одного пользователя у другого, секреты в коде или логах, небезопасную десериализацию, XSS, SSRF, новые или
незакреплённые зависимости. Только достижимое, у каждой находки путь от ввода до вреда и уровень: critical, high,
medium или low. Находки идут в раздел ошибок отчёта с пометкой «безопасность».

Сканеры безопасности в ревью не входят. В наших прогонах (ноябрь 2026) проверка изменений в плагине OpenAI Codex
Security не запустилась три раза из трёх, включая запуск через `codex exec` без интерфейса; Claude Security от
Anthropic проверяет только закоммиченное и сам спрашивает о цене. В последнем упавшем прогоне Codex проверил те же
12 изменённых файлов сам: 77 секунд на всё, две находки (medium и low).

### После твоего согласия

Каждый круг идёт так. На каждую подтверждённую ошибку — падающий тест, который падает на самой ошибке (а не на
импорте или опечатке), фикс и тесты этого места; «да» покрывает места, которые отчёт назвал для находки, — отчёт
называет, где та же логика повторяется, например вторую версию зеркального файла, — а ту же ошибку, найденную где-то
ещё, сначала показывают тебе; затем один полный прогон тестов проекта; затем повторное ревью только исправлений.
Агент ведёт список исправленных мест, и у повтора своё короткое задание: эти места, код, который их вызывает, код,
который вызывают они, и их тесты — а не вся правка заново. В Claude Code это одна задача Codex и один субагент Claude
на уровне `medium` на все исправления (без Codex — один субагент); если исправления в нескольких группах, такая пара идёт в каждую
группу, где чинили. В Codex так же, но один субагент.

Когда в круге чинить нечего или ты принял остаток, работа заканчивается один раз упрощением: Codex перечисляет
упрощения, ничего не меняя, а агент тем временем сам проходит дифф — повторное использование, повторы и мёртвый код,
лишняя работа, частные случаи там, где надо поменять общее правило, а в текстах навыков и документации — повторы и
противоречия правил (в том числе между двумя версиями и README), правила длиннее, чем нужно агенту, и лишние вызовы.
Из списка Codex агент отбрасывает вкусовщину и то, что меняет поведение или задевает код вне правки, и применяет
остальное вместе со своим; затем тесты и одно повторное ревью того, что поменяло упрощение, — что поведение не
изменилось. В Codex список даёт свежий субагент. На двух законченных правках после ревью Codex нашёл 23 настоящих
упрощения без токенов Claude (4,4M своих, 0,26M без чтения кеша), агент Claude с теми же направлениями — 14, вместе —
31 из 37; `/simplify` нашёл 17 за вчетверо больше токенов Claude, чем агент (65M против 14M с чтением кеша), и в
одной из двух правок поменял поведение.

Находки, о которых уже сообщал прошлый круг и по которым ты уже решил, отбрасываются, кроме той, которую исправление
должно было убрать, а она осталась. Если два круга подряд находят только крайние случаи в одном и том же месте, навык
останавливается и спрашивает, упростить подход или принять ограничения. После третьего повторного круга он
останавливается в любом случае и спрашивает: продолжать, упростить подход или принять остаток; при этом говорит,
сколько настоящих ошибок принёс каждый круг. Спрашивает простыми словами: что продолжает идти не так, с примером, и
по каждому варианту — что ты получаешь и что теряешь.

«Да» покрывает только те находки, которые ты видел: находки, пришедшие позже, например от прохода безопасности,
чинятся после того, как ты их увидел и сказал «да».

### Без Codex

Лимит, нет входа или ошибка модели: навык не повторяет попытку и не меняет модель. (Ревьюер Codex, ничего не
выдавший за свой срок — 15 минут, 30 для задания на всё изменение, — только останавливается и отмечается как не закончивший.)
Говорит об этом одной строкой, поднимает встроенное ревью на уровень (`low` до `medium`, `medium` до `high`; `high` остаётся),
вне финального ревью при нескольких группах добавляет одного субагента Claude с заданием на всё изменение, отдаёт сверку с планом субагенту со свежим контекстом и больше не зовёт Codex в этой сессии, пока ты не скажешь,
что он вернулся.

### Время и стоимость

По прогонам на трёх диффах замера с моделью класса Opus: лёгкое ревью заняло 2–2,5 минуты и примерно
$0,70–$1,00, обычное — около 5 минут и $1,40. Сами проверки идут 1,5–2 минуты; остальное — воспроизведение
находок. Ревью по группам дольше: на правке в 190 строк и двух группах ревьюеры Codex шли 4,5–5 минут, субагенты Claude —
9–14 (один прогон).

## handoff

Запускается, только когда ты набираешь `/duck-factory:handoff`, при желании — с тем, чем займётся следующая
сессия. Пишет `.tmp/handoff/<имя>.md` или обновляет файл, который у этой работы уже есть:

```markdown
# Падение load на пустом файле — передача, 2026-11-11

Status: active

Когда переданная этим файлом работа закончена, поменяй строку Status на `done`; когда брошена — на `dropped`.

Сначала сверь этот файл с реальностью: `git status` и `git log -3`, работают ли процессы из раздела «В работе»,
существуют ли названные здесь файлы. Скажи пользователю, что расходится, до любых действий.

Цель: `store.load` падал на пустом файле; должен возвращать [].

Ограничения: cli.py не трогать без отдельного согласия.

Прочитать сначала: store.py:6-10 (фикс), tests/test_store.py:12-24 (два новых теста).

Решения и почему: файл из одних пробелов считается пустым; битый непустой JSON по-прежнему даёт ошибку.

Сделано и проверено:
- фикс лежит в рабочем дереве — `git status --short` показывает store.py и tests/test_store.py

Сделано, не проверено: новые тесты ни разу не запускались — команде тестов нужно было разрешение.

В работе: незакоммиченные правки в двух файлах, ветка main; фоновых процессов нет.

Осталось: прогнать тесты без фикса и с ним; ревью; коммит.

Следующий шаг: прогнать тесты без фикса и увидеть, что два новых падают.

Ловушки: составные команды оболочки здесь требуют отдельного одобрения; запускать по одной.

Ждёт пользователя: cli.py:21 падает без notes.json — отдельная ошибка, не трогал.

Откат: работа началась с коммита adb43c6; `git checkout -- store.py tests/test_store.py`.
```

Важнее всего абзац о сверке с реальностью: файл устаревает, как только между сессиями что-то меняется, и сам может быть неверен.
В проверке, где фикс откатили за его спиной, следующая сессия начала со слов «файл передачи расходится с
репозиторием» и спросила, прежде чем что-то делать.

Строка `Status` работает как в плане: `active`, пока переданную файлом работу не закончили (`done`) или не бросили
(`dropped`); фраза под ней велит сессии, закончившей работу, её поменять. [Хуки](#хуки) называют активный файл
передачи с его датой при старте сессии, а агент читает его, только когда ты просишь продолжить эту работу, —
достаточно сказать «продолжаем»; после сжатия они называют его снова, чтобы сессия, работающая по нему, заново
прочитала ловушки и решения. Файл без строки `Status`, записанный прежней версией, не называется. Решения файла
передачи со `Status: done` `grill` считает прежними решениями, как решения принятого плана.

## Хуки

Оба плагина несут один и тот же небольшой скрипт (`scripts/context_hooks.py`, только стандартная библиотека
Python, читает файлы и ничего не пишет). Плагин для Claude Code запускает его на двух событиях:

| Событие | Что печатает скрипт | Куда это идёт |
|---|---|---|
| `PreCompact` | просьбу сохранить пять вещей под своими заголовками (ниже) и пути активных планов и файлов передачи | в указания для сводки при сжатии |
| `SessionStart` после сжатия | каждый план из `.tmp/plans/` со `Status: active`, три новейших целиком, пока весь вывод укладывается в лимиты обеих программ (9500 единиц UTF-16 для Claude Code, 19 000 байт UTF-8 для Codex); пока не укладывается, самый большой уступает место своему пути с просьбой прочитать; три новейших активных файла передачи из `.tmp/handoff/` — путём, с просьбой заново прочитать ловушки и решения, если сессия работает по нему | в контекст сессии |
| `SessionStart` новой или возобновлённой сессии | по строке на активный план и на активный файл передачи, по три новейших: путь, когда он менялся, и что агент читает его, только когда ты просишь продолжить эту работу | в контекст сессии |

Плагин для Codex запускает его только на `SessionStart`, с тем же выводом: то, что печатает хук `PreCompact`, Codex
игнорирует (см. [Codex](#codex)).

Что сводку просят сохранить и почему. За 24 сжатия в одном реальном проекте агент после них 33 раза возвращался
в журнал сессии; вот за чем он туда ходил и что сводка размывает:

- **Точные команды**, которыми получены результаты, ещё нужные в работе, и которыми запущено то, что ещё
  работает. Обычная сводка говорит, что сделано, но не как: за этим в журнал ходили чаще всего.
- **Длинные материалы**: тексты, которые ты вставлял, отчёты субагентов, большие выводы инструментов — где лежит
  каждый.
- **Сделано, не проверено**, и докуда дошла долгая работа: после сжатия «сделал» и «проверил» сливаются.
- **Ждёт пользователя**: на что ты согласился, а на что нет. «Дальше: сделать X» читается как разрешение.
- **Действующие поправки**: что ты сказал о способе работы — как правила, с числом повторов.

Чего не просят намеренно: состояние диска (git можно спросить заново, а за секунды после сводки ничего не
изменилось), текст плана (он возвращается целиком), правила проекта (Claude Code перечитывает их сам).

- Планы ищутся в каждой `.tmp/plans/` от каталога сессии вверх до корня репозитория.
- Строкой `Status:` считается только первая строка текста под заголовком, простая или жирная; цитата, заголовок,
  пункт списка или строка ниже — не статус самого файла.
- Если ты дал свои указания в `/compact <указания>`, хук `PreCompact` молчит.
- План, оставленный `active`, возвращается после каждого сжатия и называется при каждом старте: он закрывается,
  когда ты принял результат.
- Возобновлённая сессия получает только строку, а не план: её история цела, и печать плана при каждом
  возобновлении добавляла бы по копии. Вывод хука идёт в конец разговора, поэтому кеш промптов не ломается: с
  хуком и без него при возобновлении из кеша читались те же 15 080 токенов.
- Если у проекта есть свои хуки сжатия, эти работают рядом с ними, а не вместо.
- Проверено в живой сессии: после `/compact` в сводке появились дополнительные заголовки после стандартных, а
  модель назвала путь плана и контрольное слово из него, не читая файлов. В живой сессии Codex модель назвала
  активные план и файл передачи с их датами и что ей велено с каждым делать, не запуская команд и не читая файлов.
- Не замерено: становится ли работа после сжатия лучше от дополнительных заголовков. Повторяющуюся поправку
  сохранение её текста не лечит: в том же проекте одна была в сводке 8 раз из 9, и её всё равно приходилось
  повторять.

## Codex

Тот же конвейер для Codex CLI лежит в `plugins/duck-factory-codex` и работает целиком внутри Codex.

```bash
codex plugin marketplace add ilkruglov/duck_factory
codex plugin add duck-factory@duck-factory
```

Затем открой `/hooks` в Codex и разреши хук плагина: до этого Codex его не запускает и спросит снова, когда
обновление поменяет скрипт.

Чем отличается от версии для Claude Code:

| | Claude Code | Codex |
|---|---|---|
| Кто проверяет | встроенный `/code-review` и Codex, две модели | субагенты той же модели со свежим контекстом (`fork_turns="none"`) |
| лёгкая | `low` + Codex с заданием | один общий проход |
| обычная | `medium` + Codex с заданием + Codex «адвокатом» + сверка с планом | один общий проход + сверка с планом |
| усиленная | `high` + Codex с заданием + Codex «адвокатом» + сверка с планом | один проход «адвоката» вместо общего + сверка с планом |
| Большое изменение | `high` + Codex с заданием + Codex «адвокатом», каждый на всё изменение | по субагенту на группу файлов |
| Финальное ревью | Codex и свежий субагент Claude на каждую группу файлов, одно задание, + Codex «адвокатом» | по субагенту на группу файлов |
| Упрощение в конце | Codex перечисляет, агент фильтрует список и добавляет своё | свежий субагент перечисляет, агент фильтрует список и добавляет своё |
| Вопросы в `grill` | окно вопросов, до 4 за раунд | по режиму: в Plan mode `request_user_input` (до 3 вопросов по 2–3 варианта), вне его `request_user_input_async` или `send_message_to_user_async` и всегда текстом в итоговом сообщении (до 4), иначе текстом |
| Граница работы в плане | раздел «Не трогаем» | раздел «Охват»: что работа затрагивает (новая модель Codex не пишет, что останется без изменений) |
| Навыки по теме в `grill` | подгружаются инструментом Skill | читается их `SKILL.md` |
| Проверка плана в `grill` | Codex, только чтение | субагент со свежим контекстом |
| Проход безопасности, после твоего «да» | задача Codex (без Codex — субагент), вопрос через AskUserQuestion — пока идут остальные проверки; в запуске без интерфейса — в конце отчёта | субагент, вопрос — в конце отчёта |
| `handoff` только вручную — через | `disable-model-invocation` | `agents/openai.yaml`, `allow_implicit_invocation: false` |
| `Critical paths` и `Security paths` перечислены в | `CLAUDE.md` проекта | `AGENTS.md` проекта |
| Хуки | `PreCompact` просит сводку сохранить пять вещей; `SessionStart` называет планы и файлы передачи и возвращает план после сжатия | только `SessionStart`, после того как ты разрешишь его в `/hooks`: вывод `PreCompact` Codex игнорирует; `additionalContextLimit` 5000, потому что Codex считает токеном 4 байта UTF-8 и 2500 по умолчанию мало для плана целиком |

Почему на усиленной ступени один проход, а не два. На двух замерах (три посеянные ошибки в диффе из 581 строки,
четыре посеянные ошибки других видов в диффе из 4 строк) задание «адвоката» находило ровно те же ошибки, что и
общее, в каждом прогоне, и шло в 2–2,5 раза дольше. Что оно добавляет — воспроизведение каждой находки и пробелы
в тестах, а это и нужно правке, которую нельзя откатить. Второй проход той же модели не находил ошибок,
пропущенных первым.

Честное ограничение: второй модели здесь нет. На большем замере оба задания Codex пропустили две настоящие
проблемы, которые нашёл уровень `high` другой модели. Если у тебя есть оба инструмента, версия для Claude Code
даёт более сильное ревью.

По прогонам на тех же трёх диффах замера: лёгкое ревью заняло около 2 минут, обычное — около 2,5, и каждая
посеянная ошибка была найдена без изменения дерева.

Чтобы обновить, установи заново: `codex plugin remove duck-factory@duck-factory`, затем `codex plugin add
duck-factory@duck-factory`.

Строки для твоего `AGENTS.md`, чтобы навыки запускались сами:

```markdown
- Нетривиальная задача (новая фича или модуль, выбор подхода, правка в нескольких местах, неясная цель):
  сначала навык `grill`, потом код.
- После своей законченной правки кода, до отчёта и коммита: навык `review`, один раз. Если тебя запустили
  ревьюером чужого диффа, навык не нужен: просто проверь.
```

Второе предложение важно, когда другой инструмент зовёт Codex ревьюером: без него обычная просьба проверить
могла бы запустить навык целиком.

## Требования

- Claude Code со встроенным `/code-review`.
- Для второго мнения и проверки плана: плагин `codex@openai-codex` с выполненным входом. Без него `review`
  работает только с Claude. Codex берёт модель и уровень рассуждения из своей настройки: `~/.codex/config.toml`,
  `.codex/config.toml` доверенного проекта.
- `python3` версии 3.9 или новее в PATH: он запускает хуки.
- `timeout` из coreutils (`gtimeout` на macOS): под ним идёт каждый вызов Codex.
- В проектах `.tmp/` стоит в `.gitignore`: туда идут планы, файлы передачи и скрипты воспроизведения.

## Установка

```bash
claude plugin marketplace add ilkruglov/duck_factory
claude plugin install duck-factory@duck-factory
```

Навыки, которые должны запускаться сами, выбираются гораздо надёжнее, когда твой `CLAUDE.md` называет их по
имени. Добавь строки вроде этих:

```markdown
- Нетривиальная задача (новая фича или модуль, выбор подхода, правка в нескольких местах, неясная цель):
  сначала навык `duck-factory:grill`, потом код.
- Ревью: навык `duck-factory:review`, один раз после законченной правки кода, до отчёта и коммита.
```

## Настройка под себя

Навыки — обычный Markdown; после правки подними версию и переустанови плагин или держи свой форк.

- **Пороги ступеней**: таблица в `skills/review/SKILL.md`, шаг 1.
- **Модель Codex**: `model` и `model_reasoning_effort` в `~/.codex/config.toml`; навыки модель не передают.
- **Куда идут планы и файлы передачи**: `.tmp/plans/` и `.tmp/handoff/` в тех же двух навыках, в
  `skills/handoff/SKILL.md` и в `scripts/context_hooks.py`.
- **Критичные пути** проекта: заголовок `Critical paths` в его `CLAUDE.md` (для Codex — в `AGENTS.md`).
- **Чувствительные пути** проекта: заголовок `Security paths` в том же файле; что считать находкой
  безопасности — его `SECURITY.md`.

## Стенд

`evals/bench.py` собирает небольшой синтетический проект (хранилище заметок) и запускает на нём навыки в любой
из двух сред (Linux или macOS: прогон, не уложившийся во время, останавливается группой процессов):

```bash
python3 evals/bench.py list
python3 evals/bench.py review feature --harness claude                       # установленный плагин
python3 evals/bench.py review data --harness claude --plugin-dir plugins/duck-factory   # рабочая копия
python3 evals/bench.py grill inferred --harness codex
```

- **Случаи для ревью** — репозиторий с незакоммиченной правкой, в которой посеяны ошибки, не ловимые тестами
  проекта: `small` (один файл, одна ошибка, лёгкая ступень), `feature` (три файла кода, один из них новый, три
  ошибки, обычная ступень), `data` (только таблица CSV, которую читает код, две ошибки). Итог печатает строку
  ступени, на какие посеянные строки ссылается отчёт, время и осталось ли рабочее дерево нетронутым.
- **Запросы для grill** — те, что должны начать опрос; те, что не должны (ошибка, опечатка, вопрос); список с
  «делай всё» (первый раунд обязан спросить, что из него делать вообще); две задачи, названные в запросе (такого
  вопроса быть не должно); задача без кода (план есть, проверки его другой моделью нет).

Посеянная ошибка считается найденной, когда итоговое сообщение ссылается на её строку как `файл:строка` или `файл#Lстрока` — отчёт
навыка и так обязан это делать. Обе среды оцениваются только по итоговому сообщению, а не по следу команд и
прочитанных исходников. Это всё равно подсказка: читай отчёт. Прогон без итогового сообщения (среда упала, не
уложилась во время или ничего не ответила) показывается как неудавшийся, с концом вывода ошибок, а не как
пропущенные ошибки. Один прогон — одна проба; повтори его, прежде чем сравнивать две версии навыка. Прогоны
лежат в `.tmp/evals/`.

Прогоны не изолированы от твоих настроек: глобальный `CLAUDE.md` или `AGENTS.md`, называющий навыки по имени,
заставляет их срабатывать охотнее, чем одни их описания.

## Ограничения

- Проверено на Linux с Claude Code и моделями класса Opus; замер ступеней сделан на одном репозитории и ошибках
  одного вида (логика выбора пути и окружения). Числа в этом файле — с тех прежних замеров, а не с
  синтетического проекта из `evals/`.
- Хук для Codex не проверен на Windows без WSL: Codex может запускать его команду через `cmd.exe`, а тот не
  раскрывает `${PLUGIN_ROOT}`.
- Хукам нужно, чтобы в плане была строка `Status: active`; в плане, написанном версией до 0.2.0, её нет, и он не
  возвращается, пока ты её не добавишь.
- В запуске без интерфейса (`claude -p`) окно вопросов недоступно, и `grill` спрашивает текстом.
- `review` проверяет находки воспроизведением, поэтому лёгкое ревью занимает около двух минут, а не одну.
- `review` считает строки без учёта отступов, поэтому правка, где сдвиг отступов смешан с настоящими
  изменениями, может быть посчитана меньше, чем она есть, и получить ступень легче. Ревьюеры всё равно читают
  дифф целиком; по счёту выбирается только глубина.
- Тесты навыков проверяют, что правило есть в тексте, а не что оно сформулировано верно; что правило заставляет
  агента делать, проверяют ревью и стенд.
